# فاز ۰ — ممیزی و پایه (HD-2D Upgrade)

> بازه: نوبت ۵۰ · تاریخ: 2026-10-07 · وضعیت: **پایان‌یافته** · در این فاز **هیچ کدی از بازی تغییر نکرد** (طبق دستور).

## ۲) ابزارهای ممیزی (جدید، در `tools/`)

- `tools/audit0.mjs` — بوت Playwright، سه نما، ۷ اسکرین‌شات صحنه + ۴ اسکرین‌شات UI، بنچ CPU (آپدیت/رندر/present)، اندازه‌گیری rAF، کاوش قابلیت‌های WebGL2 → `shots/p0_metrics.json`.
- `tools/analyze0.py` — کمّی‌سازی رستر: تعداد رنگ (۶-بیت)، روشنایی، share رنگ غالب هر تایل، خودهمبستگی عمودی زمین، کنتراست اسپرایت/پس‌زمینه، سهم لبه‌ی نرم → `shots/p0_audit.json` + شیت `shots/p0_baseline_sheet.png`.

روش اسکرین‌شات: **بوم بازی برای ممیزی پیکسلی بی‌اعتبار است** (`toDataURL` روی بومِ بدون `preserveDrawingBuffer` خارج از همان فریم خالی/سیاه برمی‌گردد) → رستر صحنه مستقیماً از `game.render(sc)` گرفته و PNG می‌شود (`p0_raw_*.png`، پیکسل‌دقیق). بوم هم جداگانه dump می‌شود (`p0_webgl_*.png`) و شات کامل صفحه با UI (`p0_full_*.png`).

`tools/bench.mjs` (Node، بدون مرورگر) همین اعداد را تأیید می‌کند: مزرعه روز ۰٫۷۵ / دانجن ۱٫۴ms. هر دو تست رگرسیون موجود پاس شدند (`render5` ۱۵/۱۵، `render6` ۲۷/۲۷).

rAF در همین محیط: میانه ۲۴٫۰–۲۵٫۰ms (p95 ≈ ۲۸) برای هر سه صحنه. **این عدد سقف نیست، کفِ محیط است**: رستری‌سازی نرم‌افزاری SwiftShader روی ۷۸۰×۱۶۸۸ حدود ۲۳ms صرف present می‌کند. پس:
- عدد CPU بالا (که تابع گلوگاه واقعی ماست) معتبر است؛
- عدد rAF **شاهد GPU نیست** و «۶۰fps روی اندروید میان‌رده» از این سندباکس قابل اثبات نیست → در فازهای بعد بودجه‌ی CPU + شمارش pass/draw-call را می‌سنجیم و این محدودیت را در گزارش‌ها اعلام می‌کنیم.

## ۴) معماری هدف (خلاصه‌ی ≤۲۰ خط — همان چیزی که فازهای ۱..۹ می‌سازند)

```
1. دو مسیر رندر: GPU (WebGL2، پیش‌فرض) + CPU فعلی (fallback کامل؛ همان Raster→ImageData→Canvas2D)
2. انتخاب در بوت: webgl2 موجود && Q.gl != 0 → GPU؛ در غیر این صورت CPU (بدون هیچ تغییری در منطق)
3. دنیای منطقی ثابت: گریدهای ۱۶px، نقشه‌ها، سیو، A*، نبرد — دست‌نخورده می‌مانند
4. یک آطلس ۲۰۴۸² (NEAREST، پدینگ ۱px): کاشی، اسپرایت، normal، emissive، فونت — همه رویه‌ای بیک می‌شوند
5. batcher: VAO + VBO داینامیک، هر اسپرایت یک quad (۴رأس/۶اندیس)، صف y-sort، ≤ ۴۰ draw call در فریم
6. دوربین diorama: ortho شیب‌دار (tilt ≈ ۳۵°) → صفحه‌ی زمین با پرسپکتیو ملایم، اشیا billboard ایستاده با z واقعی
7. sprite shader: albedo + normal رویه‌ای + sel-out (کانال آلفا) + rim + تینت نور محیط
8. light pass جلوسو: نور نقطه‌ای addaptive (flat array)، نور جهت‌دار ++ سایه‌ی نرم projected، emissive additive، AO رویه‌ای از ارتفاع
9. post chain: HDR RT → bright+blur(۲ میپ) → bloom؛ tilt-shift DOF (mask بالا/پایین)؛ LUT ۳بعدی ۸³ هر تم؛ وینیت/گرین؛ god-rays از ماسک نور
10. ذرات روی GPU (instanced) + shader باد روی کاشی/گیاه + انیمیشن آب
11. هر افکت دو سطح کیفیت دارد؛ Q.level تطبیقی (۲/۱/۰) → نصف‌کردن RT و حذف passها
12. UI: پنل‌های شیشه‌ای رویه‌ای (9-slice) + backdrop بلور چندفریم؛ RTL/فارسی حفظ
13. صفر asset خارجی؛ فونت گلیف‌ها نیز به آطلس GPU بیک می‌شوند (UI متن = quad)
14. در end هر فراز: بوت‌تست jsdom + Playwright سه‌نما + شیت قبل/بعد + MEMORY
```

## ۶) آنچه به هدف نرسید (صادقانه)

- **همه‌ی هفت مورد**: baseline فعلی «پیکسل‌آرت ۲بعدی تمیز و مرتب» است، نه HD-2D. هیچ‌کدام از سه ستون اصلی (دوربین سه‌بعدی‌نما، نور/پست‌پروسس، تایل/اسپرایت غنی) وجود ندارد.
- **در سنجش فریم‌تایم**: هیچ عدد معتبری از «اندروید میان‌رده» در دست نیست (فقط سنجه‌ی CPU و شمارش فراخوانی‌ها از این سندباکس). بودجه‌ی ۸ms باید در فاز ۹ با پروفایل مرورگر + بودجه‌ی CPU ارزیابی شود و صریحاً «تخمین» برچسب بخورد.
- **رندر GPU واقعی سنجیده نشد**: SwiftShader نرم‌افزاری است؛ اعداد GPU (fragment cost، fill-rate) از این محیط قابل استخراج نیست؛ فقط صحت/ظاهر پاس‌ها اثبات می‌شود.
- **اتوماتیک‌بودن «قضاوت زیبایی‌شناسی»**: سنجه‌های عددی (رنگ/تخت‌بودن/کنتراست/DOF) به‌دست آمد، اما بخشی از حسّ Octopath فقط با چشم و مقایسه‌ی شیت قابل قضاوت است.

## ۶.۵) باگ‌های ظاهری کشف‌شده در ممیزی (فهرست کار، خارج از دامنه‌ی فاز ۰)

۱. **باندِ letterbox در پرتره**: دنیای مزرعه ۴۸۰×۳۲۰ است ولی ناحیه‌ی بازی در موبایل پرتره ۱۹۵×۳۴۹ → دوربین `cy` را روی ‎-۱۴٫۵ clamp می‌کند و ۱۴٫۵px بالا/پایین صحنه **بدون هیچ تایلی** می‌ماند (رنگ پس‌زمینه‌ی CSS، عملاً نوار تیره). الان فقط در موبایل پرتره دیده می‌شود.
۲. تایل‌های خالی/تکراری: سهم رنگ غالب هر تایل ۰٫۸۰ (مزرعه) یعنی هر تایل تقریباً تک‌رنگ است → برای فاز ۴.
۳. موب‌ها در نبرد کنتراست کم دارند (dL=۳۵ در برابر پس‌زمینه‌ی دانجن) — برای فاز ۵.

## ۷) یافته‌های فنی مهم برای فازهای بعد (درس‌های تازه)

1. **اسکرین‌شات بصری**: `toDataURL` بوم خارج از فریم رسم → سیاه؛ مرجع ممیزی = رستر `render(sc)` (پیکسل‌دقیق، بدون مقیاس مرورگر).
2. rAF در headless (SwiftShader) ≈ ۲۴ms کفِ محیط است؛ مقایسه‌های بعد/قبل باید در **همان سشن و هم‌دقیقه** انجام شود (هم‌راستا با درس ۱۴ قبلی).
3. تفکیک صحنه/رندر تمیز است: `farmScene.render(raster)` و `run.render(raster)` نقطه‌ی تزریق مسیر GPU هستند؛ `buildFloorCache` و کش‌های `sprCache` آماده‌ی تبدیل به آطلس‌اند.
4. مدل نور فعلی دوگانه است: مزرعه = LUT ضربی شب (`night.js`)، دانجن = استمپ‌های شعاعی + LUT (`art/light.js`). فاز ۲ باید این دو را در **یک مدل نوری** با هم جمع کند و مسیر قدیم به‌عنوان fallback بماند.
5. روز/شب مزرعه در سیو نیست (بوت همیشه `dayT≈0` = صبح) — برای فاز ۲ (چرخه‌ی روز/شب) باید تصمیم طراحی گرفته شود.
6. گلوگاه مسیر فعلی **present** است (۰٫۲–۰٫۵ms صرف `putImageData`+`drawImage`), نه رندر (۰٫۵–۱٫۷ms). این یعنی مسیر CPU جا دارد اما GPU برای پست‌پروسس لازم است.

## ۸) قدم بعدی (فاز ۱، فقط پس از تأیید این گزارش)

batcher اسپرایت WebGL2 + آطلس رویه‌ای (بیک در بوت) + دوربین diorama با tilt + کاشی روی صفحه‌ی شیب‌دار + billboard عمودی + حرکت زیرپیکسلی دوربین + فیلتر NEAREST تمیز؛ با حفظ کامل مسیر CPU به‌عنوان fallback و بوت‌تست jsdom در پایان.
